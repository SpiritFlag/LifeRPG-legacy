# LifeRPG v2 — 출력 상한·숫자 제약·운영 예산 정렬

2026-10-15. [캠페인 재개](V2-OPENAI-CAMPAIGN-RESUME-20261015.md)에서 발견한 출력 잘림과 `importance` 범위 오해를 수정했다. **이번 실제 OpenAI 요청 0회.** 운영 DB 접근·변경, 기존 평가 DB 열기, 예약 해제, 예산 초기화, 배포는 하지 않았다.

## 변경과 원인

- `GM_MAX_OUTPUT_TOKENS`의 기본값과 애플리케이션 설정 상한을 **16,384**로 변경했다. 입력 상한 16,384, 모델 `gpt-6.1-sol`, reasoning `medium`, 가격표는 유지했다. `.env.openai.example`과 기존 로컬 환경파일의 출력 상한도 맞췄다. 로컬 파일은 출력 상한 한 줄만 변경했고 키·기존 합성 예산·승인 게이트 값은 바꾸지 않았다.
- 기존 Schema 변환기는 Zod의 숫자·배열·문자열 제약을 모두 제거했다. 서버는 `importance=0..3`을 요구했지만, 모델의 부분 출력에는 8·9가 있었다. 이제 지원되는 제약을 Zod 원본에서 그대로 가져오므로 별도 숫자 목록과 서버가 어긋나지 않는다.
- 기본 Structured Outputs 지원 목록에 있는 `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `multipleOf`, `minItems`, `maxItems`, `pattern`, 허용된 `format`을 전송/사전 점검한다. 현재 실제 계약에 없는 키를 억지로 추가하지 않는다. [공식 지원 범위](https://developers.openai.com/api/docs/guides/structured-outputs#supported-schemas)
- 공식 기본 지원 목록에 명시되지 않은 `minLength`/`maxLength`는 필드 `description`으로 전달하고 Zod 검증을 유지한다. 현재 설치된 Zod 4.6.7은 문자열 길이를 **Unicode 코드 포인트**로 센다. GM 지침도 이를 따르며, 이름·능력치 이름·슬롯의 trim/공백 금지와 `progress <= target`처럼 필드 간 제약도 명시한다. 참조·소유·중복 보상·퀘스트 상태 전이 등 기존 도메인 검증은 그대로다.
- GM 지침에 **importance는 정수 0~3, 3이 최고이며 10점 척도가 아님**을 명시했다. 자유로운 창작, 판정 독립성, 현실/판타지 분리, 비공개 경계, 삭제, 정체성 성장 규칙을 유지했다. 분량을 줄인 지침의 실모델 행동 동등성은 다음 유료 평가에서 확인해야 한다.

주요 숫자 계약:

| 필드 | 전송 및 서버 허용 범위 |
|---|---:|
| `memories[].importance` | 정수 0~3 |
| `xp_delta` | 정수 -1,000~1,000 |
| `expected_version` | 정수 0~1,000,000 |
| 능력치·효과 값, inventory delta | 정수 -1,000,000~1,000,000 |
| 캐릭터 level, quest target | 정수 1~1,000,000 |
| quest progress | 정수 0~1,000,000, 별도로 `progress <= target` |
| `advance_time.ticks` | 정수 1~1,000 |
| 판정당 memories / operations | 최대 5 / 32개 |

MCP 5개, RPG 종류와 자유로운 정의, 최대 작업 수, 원자적 확정, 삭제 출처 추적은 변경하지 않았다. Schema의 추가 제약 때문에 기존 기억 공간이 줄어드는 회귀를 발견해, 같은 UUID 정의 공유·내부 `$defs` 이름 단축·단일 참조 정의의 정확한 인라인으로 압축했다. 판별자·값·설명·속성 이름을 문자열 치환하지 않는다. `oneOf` 배타성 증명과 `anyOf` 변환은 유지하며, 독립 Ajv 검증기로 의미 보존을 검사한다. 입력 한도와 4,096 프레이밍 여유, 기억 선택 정책은 바꾸지 않았다.

## 예약과 운영 월 $10

예약은 기존 동적 계산을 사용한다. 입력의 최악 단가(일반/캐시 읽기/쓰기 중 최대)와 출력 상한으로 계산하며, 완료 후 실제 usage로 정산한다. 미확정 응답은 예약을 계속 유지한다.

| 항목 | 계산 | 최대 예약 |
|---|---|---:|
| 입력 | 16,384 × $2.50 / 1M | $0.040960 |
| 출력 | 16,384 × $10 / 1M | $0.163840 |
| **합계** | **204,800 microUSD** | **$0.204800** |

기존 $0.061440 대비 약 3.33배다. reasoning 토큰은 출력 usage에 포함되므로 중복 가산하지 않는다. 이 값은 호출당 최대 **예약**이며 고정 요금이나 실제 청구액이 아니다. 단가는 기존 표준 tier 가격표와 [공식 Sol 모델 문서](https://developers.openai.com/api/docs/models/gpt-6.1-sol)를 따른다.

운영 정책의 별도 설정은 `GM_OPERATING_MONTHLY_BUDGET_MICRO_USD=10000000`(기본 $10)이다. 신뢰된 운영자 함수 `configureOperatingMonthlyBudget(db, operatingMonthlyBudget(env))`는 명시적으로 실행할 때 월 한도만 설정한다. 일별·누적·사용자별 한도, 사용량/예약, blocked 작업은 변경하지 않는다. **이번에는 이 함수를 신규 임시 테스트 DB에서만 검증했으며 운영에 적용하지 않았다.** 월 초기화는 ledger 삭제가 아니라 기존 UTC 월별 집계이고, 미확정 예약은 월 경계를 넘어 계속 차감한다.

빈 사용량과 다른 한도에 여유가 있는 조건에서 $10에는 최대 예약액 기준 48건($9.830400)이 들어간다. 실제 완료 비용으로 정산하면 허용 호출 수는 달라진다. 사용자별 기본 한도 $0.10과 예전 합성 실행기의 $0.15 한도는 새 예약액보다 작아서 계속 차단한다. 운영 전환 시 사용자별·일별·누적 한도를 별도로 확정해야 하며, $10 정책을 이유로 이를 자동 상향하지 않는다.

## 다음 실모델 평가

무과금 점검:

```powershell
npm run gm:preflight
```

`budget_applied:false`, `ledger_checked:false`, `paid_calls_authorized:false`는 의도된 결과다. DB 현재 잔여 예산이나 계정 모델 접근을 보증하지 않는다. 환경변수의 명시적 설정이 기본값보다 우선하므로 다른 호스트에서도 출력 16,384를 확인한다.

다음 순서는 **별도 유료 승인 → 새 격리 평가 계획 고정 → 탄생 1건 → 성공 시 승인된 후속 사례**다. 기존 실행기를 바로 `--resume-approved`로 실행하지 않는다. 그 실행기는 과거 frozen config와 남은 모든 호출의 $0.50 예약 상한을 검사하므로 새 설정을 거부하는 것이 정상이다. 새 승인에 맞는 계획에서 이전 호출/예약을 이월하고 게임 규칙·지침·schema·모델·reasoning을 실행 전에 고정해야 한다.

기존 캠페인의 실제 요청은 누적 2회, 누적 예약 $0.122880, 정산 비용 $0.025786, 미확정 예약 $0.061440이다. 이 이력은 그대로 보존했다. **기존 누적 $0.50 제한을 유지한다면 새 최대 예약은 한 건만 더 들어간다**: $0.122880 + $0.204800 = $0.327680. 두 건이면 $0.532480으로 넘는다. 운영 월 $10은 합성 평가의 지출 승인이나 예산 초기화 권한이 아니다.

첫 실모델 평가에서 확인할 사항: 새 bounds/format을 포함한 schema의 공급자 수락, 16,384 안의 완료와 실제 출력/추론 사용량, importance 준수와 서버 확정, 탄생의 직업·스킬·퀘스트·NPC·기억 품질, 공개 장면의 비밀 누설, 추가 성찰 호출 없이 장기 기억을 이어가는지, 지연/비용. 로컬 통과는 실모델 성공 보증이 아니다. 실패하면 추가 재시도 없이 원인을 기록하고 중단한다.
